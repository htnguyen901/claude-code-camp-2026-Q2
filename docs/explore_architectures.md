# Explore Agent Architecture
## 1. An agent file with referenced files eg AGENT.md, @~/docs/*.md

The simplest agent is creating an 'agent file' and possibly import other files that are read conditionally when needed.

We would attempt to create an agent file and see if it can connect to the MUD and complete a simple goal eg: find the bakery and list what is on the menu

We would want to use a simple model and scale up

### Technical Observations:
Using haiku 4.5 - high effort as our Coding Harness we created a CLAUDE.md with simple prompt, and told it would need to manage its own local memory via simple markdown file. We provided it with the location of the MUD and player credentials.

Agent created temporary python scripts and code files to manage the socket connection and executed commands to play the game
Agent did not have enough information about Text User Interface of the MUD to login and see its mistake
Agent found the bakery and told me what was on the menu despite failing to login - this could be due to luck
Agent wrote state data to player.md and and a thorough observation of the world to world.md

### Technical Conclusion

The agent successfull connected to the MUD and gave us the list of items in the bakery, as well as basic player info and a short summary/observation of the discovered areas of the MUD world. However, a huge amount of token was spent and login were still a hit or miss (never fully fixed the login problem)

A coding harness alone is not a good fit for operating the MUD as it wastes too much tokens and does not guarantee a successfull connection every time.

The deterministic login and connection flow should be handled by a reusable MUD SDK rather than regenerated by the model on every attempt.

A specialized agent loop, potentially using an MCP server connected to the MUD SDK, would provide better reliability, visibility, and token efficiency.

## 2. Agent skills driven by main Agent eg ~/.skills

A very common way to drive specific functionality is via Agent Skills which is an open format for agents adopted by many coding harness and Agent SDK

### Technical Observation

**Initial Skill Creation (Haiku 4.5, via official skill-creator)**
The Agent used Haiku 4.5 with the official skill-creator to generate a `skill.md` and accompanying Python scripts. The resulting scripts encoded a rigid, hard-coded navigation/execution flow rather than a generalized approach. Initial invocation returned no output; the Agent resorted to writing ad hoc temporary scripts to debug the MUD client connection. It eventually completed the task and reported menu contents, but on a follow-up request ("find a fountain and drink water"), it extended the existing hard-coded script rather than generalizing it. Later fix attempts failed and the Agent bypassed the skill wrapper entirely, writing new temporary scripts instead. Because the Agent retains no persistent memory of the game world, it repeatedly rebuilds or edits scripts to re-explore already-visited areas. The scripts are also location-dependent, hard-coding actions relative to a fixed starting position and requiring manual updates whenever the player starts elsewhere.

**Redesign Attempt**
Asked to redesign the skill for a generalized execution flow with persistent memory:
- Haiku 4.5 responded with extensive clarifying questions about execution flow, goal decomposition, and request scope before proceeding.
- Sonnet 5 attempted the redesign directly but consumed a very large number of tokens completing it.

**Continued Exploration (Haiku 4.5, redesigned skill)**
Tasked with finding and defeating a minotaur in the Newbie Zone:
- The Agent began by reading current game state and memory files, then formed an exploration plan (heading north, leveling up if needed).
- During exploration it was attacked and died, updating player state throughout and maintaining accurate awareness of game state.
- It failed to locate the minotaur despite alternate strategies (e.g querying NPCs), and proactively asked whether to prioritize scouting or leveling up.
- When told the Minotaur was in the "Red Room" and directed to make a decision itself, the Agent decide to scout first, the Agent explored but could not find the target "Red Room."
- The Agent failed to update memory files during this phase, treating memory upkeep as a deferred administrative task rather than interleaving it with real-time exploration. (Not sure if fail to update memory was because the request wasn't made by calling the /mud-player skill directly)

I could see it struggles to maintain and keep up-to-date with the memory files, especially when they grow large. 

I think we should have dynamic task management and goal decomposition in placed.

The Agent made good decision of scouting the target first to determine the requirements needed to defeat it. But this thought process might not be the same for every loop/request. I would call this Focus Mode where I like to stay within the main quest. But we should have options for Agent to play in different Modes

### Technical Conclusions

Agent skills does work well, but for complex task we will need better state, player and world management. We need to have auditable visibility on token usage, agent's plan, agent progress as well as its journey. We want an agent that acts in an overall (adaptive to the journey) plan rather than wondering, thinking and making up new/next plan as it goes.

We might need to define Player Persona, which describes how the player likes to play, eg: Easy Mode, Difficult, Risk Mode, etc.

We should see a goal decomposition or planning to see how agent will reason the goal.
